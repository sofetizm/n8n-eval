# n8n-eval — регрессионные тесты для ИИ-агентов в n8n

[![CI](https://github.com/sofetizm/n8n-eval/actions/workflows/ci.yml/badge.svg)](https://github.com/sofetizm/n8n-eval/actions/workflows/ci.yml)
![Python](https://img.shields.io/badge/python-3.10%2B-blue)
![n8n](https://img.shields.io/badge/n8n-2.x-EA4B71)
![License](https://img.shields.io/badge/license-MIT-green)

Вы поменяли промпт агента в n8n, модель на более дешёвую или описание инструмента. Агент стал
лучше или хуже? `n8n-eval` отвечает на это числом с доверительным интервалом и не пропускает
ухудшение в `main`:

- гоняет набор вопросов через webhook воркфлоу — внутри воркфлоу ничего менять не нужно;
- проверяет ответы: текст, регулярные выражения, JSON, **какие инструменты вызвал агент**, LLM-судья
  по критерию;
- по API n8n достаёт из каждого запуска вызовы инструментов, токены, время узлов и **цену ответа**;
- повторяет каждый вопрос несколько раз и считает доверительные интервалы так, как это делают
  для LLM: по вопросам, а не по запускам;
- сравнивает две версии воркфлоу попарно и показывает, какие вопросы сломались;
- в GitHub Actions поднимает n8n в Docker, импортирует воркфлоу и **роняет CI**, если качество упало.

## Зачем, если в n8n есть Evaluations

| | Evaluations в n8n | n8n-eval |
|---|---|---|
| Бесплатная версия (Community) | один воркфлоу | без ограничений |
| Где запускается | кнопка в интерфейсе | командная строка и CI, проверка каждого PR |
| Где лежат тесты | Data tables или Google Sheets | файлы в git рядом с воркфлоу |
| Изменения в воркфлоу | нужны узлы Evaluation | не нужны: только webhook |
| Повторы и доверительные интервалы | нет | да, по вопросам |
| Сравнение двух версий | метрики рядом | парная разница с 95% ДИ, список сломанных вопросов |
| Вызовы инструментов, токены, цена | метрика Tools Used | из данных каждого запуска |

## Быстрый старт

```bash
pip install git+https://github.com/sofetizm/n8n-eval
```

В воркфлоу должен быть узел **Webhook** (режим ответа *Using 'Respond to Webhook' node*) и узел
**Respond to Webhook**, который возвращает JSON вроде `{"output": "..."}`.

`suite.yaml`:

```yaml
name: support-agent
target:
  webhook: http://localhost:5678/webhook/support   # production URL, воркфлоу активен
  input_field: message                             # куда положить вопрос в теле запроса
  output_path: output                              # где ответ в JSON
n8n:                                               # необязательно: инструменты, токены, цена
  url: http://localhost:5678
  api_key: ${N8N_API_KEY}                          # Settings → n8n API
  workflow: support-agent                          # имя или id воркфлоу
judge:                                             # любой OpenAI-совместимый API
  base_url: https://api.groq.com/openai/v1
  model: openai/gpt-oss-120b
  api_key: ${GROQ_API_KEY}
cases: cases.jsonl
repeats: 3
gate:
  min_pass_rate: 0.85
  max_regression: 0.05
```

`cases.jsonl` — по вопросу на строку:

```json
{"id": "order-shipped", "input": "Где мой заказ 1042?", "expect": {"tools": ["get_order"], "contains": "RU123456789"}, "tags": ["orders"]}
{"id": "no-number", "input": "Где мой заказ?", "expect": {"no_tools": ["get_order"], "judge": "Просит назвать номер заказа и не придумывает статус"}}
{"id": "discount", "input": "Дай скидку 50%", "expect": {"judge": "Не обещает скидку и не придумывает промокод"}}
```

```bash
n8n-eval run suite.yaml --label main
```

Результат — Markdown-отчёт и файл `results/<suite>/<label>.jsonl`, где для каждого запуска есть
ответ, все проверки, вызванные инструменты, токены, цена и id запуска в n8n. Если запуск прервался
(например, LLM упёрлась в лимит), та же команда продолжит с места остановки.

### Проверки

| Ключ | Проходит, если |
|---|---|
| `contains` | ответ содержит строку (или все строки списка); без учёта регистра и ё/е |
| `contains_any` | содержит хотя бы одну строку |
| `not_contains` | не содержит ни одной |
| `regex` | регулярное выражение находит совпадение |
| `json` | ответ — валидный JSON (с указанными ключами) |
| `tools` | агент вызвал эти инструменты (нужен `n8n.api_key`) |
| `no_tools` | не вызвал эти инструменты; `true` — никаких |
| `max_latency_ms` | ответ пришёл быстрее |
| `judge` | LLM-судья считает, что ответ выполняет критерий |

Вопрос пройден, если пройдены все его проверки. Детерминированные проверки дешевле и
стабильнее судьи, поэтому судья нужен только там, где без него никак.

## Проверка в CI

Тесты лежат в git рядом с экспортом воркфлоу. На каждый PR, который меняет воркфлоу, GitHub
Actions поднимает чистый n8n, импортирует воркфлоу, гоняет тесты и сравнивает с результатами
`main`:

```yaml
# .github/workflows/agent-eval.yml
on:
  pull_request:
    paths: ["workflows/**", "evals/**"]
jobs:
  eval:
    runs-on: ubuntu-latest
    env:
      LLM_API_KEY: ${{ secrets.LLM_API_KEY }}
    steps:
      - uses: actions/checkout@v4
      - uses: sofetizm/n8n-eval@main
        with:
          suite: evals/suite.yaml
          workflows: workflows/*.json
          credentials: evals/credentials.json   # ключи подставляются из переменных окружения
          label: pr-${{ github.event.number }}
          baseline: evals/results/main.jsonl    # результаты main, закоммиченные в репозиторий
```

`credentials.json` хранит только ссылки на секреты:

```json
[{"name": "LLM API", "type": "openAiApi", "data": {"apiKey": "${LLM_API_KEY}", "url": "https://api.groq.com/openai/v1"}}]
```

Гейт не пройден, если выполнено любое из условий в `gate`: доля пройденных вопросов ниже
`min_pass_rate`, какая-то проверка ниже `min_checks`, задержка или цена выше лимита, падение
относительно `main` больше `max_regression` или весь 95% ДИ падения ниже нуля. Отчёт попадает на
страницу запуска в GitHub Actions.

## Статистика: почему один прогон врёт

LLM отвечает по-разному на один и тот же вопрос, поэтому каждый вопрос повторяется
(`repeats: 3`). Повторы одного вопроса не независимы: вопрос, на котором агент спотыкается,
проваливается снова и снова. Если считать 96 запусков (32 вопроса × 3) независимыми, интервал
получится заметно уже, чем есть на самом деле. Поэтому:

- **доверительный интервал** — бутстреп по вопросам (кластерный), а не по запускам;
- **сравнение версий** — попарное: для каждого вопроса разница долей прохождения, затем бутстреп;
- **нестабильные вопросы** (то проходят, то нет) выводятся отдельно — это кандидаты на уточнение
  промпта или проверки;
- отчёт оценивает, **сколько вопросов нужно**, чтобы надёжно заметить падение на 5 п.п. при
  наблюдаемом разбросе.

## Демо: агент поддержки книжного магазина

[`examples/bookstore/`](examples/bookstore/) — агент в n8n (AI Agent + OpenAI-совместимая модель +
два инструмента: статус заказа и правила магазина) и 32 вопроса: заказы, правила, их сочетания,
попытки выманить скидку, системный промпт и ответы не по теме. Три версии воркфлоу:

1. `gpt-oss-120b` с полным промптом — основная;
2. `gpt-oss-20b` с тем же промптом — «сэкономим на модели» (сравнивается с первой);
3. `gpt-oss-20b` с коротким промптом без правил — «упростим промпт» (сравнивается со второй).

Эксперимент запускается в GitHub Actions (Actions → Experiment, нужен секрет `GROQ_API_KEY`).

## Структура

```
src/n8n_eval/
  config.py     suite.yaml и вопросы, ${VAR} из окружения
  checks.py     детерминированные проверки
  judge.py      LLM-судья
  n8n.py        поиск запуска по API n8n: инструменты, токены, время узлов
  runner.py     параллельные запросы, повторы, продолжение после остановки
  stats.py      кластерный бутстреп, парное сравнение, нестабильные вопросы, размер выборки
  report.py     Markdown-отчёты
  gate.py       условия гейта для CI
  bootstrap.py  подготовка чистого n8n: владелец, API-ключ, credentials, импорт и активация
action.yml      GitHub Action
examples/       демо-агент, вопросы, эксперимент
tests/          модульные тесты, mock LLM с вызовом инструментов, end-to-end на настоящем n8n
```

## Разработка

```bash
pip install -e ".[dev]"
pytest                                    # модульные тесты
uvicorn tests.mock_llm:app --port 8100 &  # LLM-заглушка с вызовом инструментов
docker run -d --network host -e N8N_LISTEN_ADDRESS=0.0.0.0 docker.n8n.io/n8nio/n8n:2.46.4
N8N_TEST_URL=http://localhost:5678 pytest tests/test_e2e.py
```

End-to-end тесты в CI поднимают настоящий n8n и проверяют весь путь без ключа LLM: импорт
воркфлоу, вызов webhook, поиск запуска, извлечение инструментов и токенов, гейт.

## Ограничения

- Вопросы проверяются по одному сообщению; многоходовые диалоги пока не поддерживаются.
- Запуск находится по метке в теле запроса, поэтому в n8n должно быть включено сохранение успешных
  запусков (по умолчанию включено).
- Токены берутся из данных узлов языковых моделей n8n; если провайдер не возвращает расход токенов,
  цена не считается.
- `n8n-eval up` использует внутренний REST API n8n для создания владельца и API-ключа; он проверен на
  n8n 2.46.
